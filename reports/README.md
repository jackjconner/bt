# Change Reports

One markdown report per landed change, organised by round.

## Directory layout

```
reports/
  README.md                 ← this file
  _template.md              ← fill-in template for new reports
  round-NNN/
    <component>.md          ← one report per component that shipped a change
    assets/
      <component>-before.cpu.calltree.txt
      <component>-after.cpu.calltree.txt
      <component>-before.speedscope.json.gz   ← open at speedscope.app
      <component>-after.speedscope.json.gz
      <component>-flamegraph.html             ← pyinstrument HTML; embedded inline
      <component>-mem.summary.txt
      profile_artifacts.parquet               ← artifact index from profiling/flamegraph.py
  _site/                    ← generated by `scripts/reports build` (gitignored)
```

`round-NNN` is zero-padded to three digits; it matches the round number written
to `.oversight/round_state.json`.

## Frontmatter convention

Every report starts with YAML frontmatter so the site generator can index
reports without parsing prose:

```yaml
---
round: 3                          # integer
component: portfolio              # one of the seven components
pr: 42                            # GitHub PR number (integer)
date: "2026-05-30"                # ISO-8601
metric: "portfolio p50_ms"        # the optimised metric
verdict: accepted                 # accepted | rejected
headline_delta: "-52x p50_ms"    # human-readable before→after summary
---
```

All six fields are required; the site generator raises if any is missing.

## Five-section structure

Every report uses exactly these five sections (H2 headings):

### 1. What it addressed
The target: which component, which metric, which hotspot in the flame graph.
Reference the round's proposal from `.oversight/round_state.json`.

### 2. How it decided
The flame-graph reading and reasoning — what paths were examined, what was ruled
out, why the chosen approach was taken.  Embed or link the *before* calltree
(`assets/<component>-before.cpu.calltree.txt`) here so the reasoning is auditable.

### 3. Pre/post profile
Before → after numbers (p50_ms, peak_mb, scaling exponent where relevant).
Embed the *after* flame graph inline — the site generator looks for the first
`assets/*.html` file referenced or present and iframes it:

```markdown
![flame graph](assets/portfolio-flamegraph.html)
```

The generator wraps any `.html` asset reference in an `<iframe>`; any `.svg`
asset reference is inlined as `<img>`.

### 4. System impact
Eval shift (signal IC, walk-forward Sharpe, cost drag) vs the golden snapshot.
Note any downstream effects on other components.  The ledger entry from
`IMPROVEMENTS.md` goes here verbatim.

### 5. Suggested next steps
What the flame graph still shows that this change did not address.  The next
round's candidate targets.

## Generating reports

The orchestrator dispatches a **report-generator sub-agent** after each swarm.
See `.claude/skills/change-report/SKILL.md` for the full protocol.

## Browsing reports

```bash
mise run setup                 # once: wire the post-commit hook (auto-rebuild)
mise run serve                 # build + serve over Tailscale HTTPS (foreground)
mise run build                 # render reports/_site/ once
```

`mise run serve` wraps `scripts/reports --serve`; `mise run build` wraps
`scripts/reports build`. Leave `serve` running in a tmux pane — it serves
`_site/` on the tailnet.

### Auto-publish + live-reload

Once `mise run setup` has pointed git at `.githooks/`, the **post-commit hook
rebuilds `reports/_site/` whenever a commit touches `reports/`** — so a report a
round lands is published automatically, with no manual `build` step.

Every rendered page polls `_site/build-id.txt` (a content hash bumped on each
render) once a second and reloads itself when it changes. So with `mise run
serve` running, an open tab **live-reloads** the instant a new report is
committed — no manual refresh. The poll is dependency-free (no websocket), so it
works cleanly through the Tailscale HTTPS proxy.
